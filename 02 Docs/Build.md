# Botlien — Build

Original blueprint written under the "Custodly" name (2026-08-04, single planning session, Antonio D'Angelo + Samuel Kim). Content below is name-corrected to Botlien; substance is unchanged from the original. Treat every timeline, comp, and access assumption as directional — re-verify against real API documentation, lender conversations, and legal counsel before committing resources.

## Positioning pivot — 2026-08-05, primary customer is now the RaaS operator, not the lender

**What changed:** Botlien's primary and immediate customer is now the RaaS operator itself, not a lender or creditor. The lender relationship isn't gone, it moves from "who we sell to first" to "who we sell to downstream, once there's real usage data and a paying RaaS customer base." This is a sharpening of the existing GTM sequencing (which already said RaaS-first), not a reversal of it — the change is treating RaaS operators as the actual, standalone customer instead of a stepping stone toward lenders.

**Why:** RaaS is growing roughly 2x faster than the broader equipment finance industry it would otherwise depend on for its first customer (RaaS market ~20% CAGR through 2030 vs. equipment finance ~10-13% CAGR, sourced 2026-08-05). More importantly, it resolves the single worst-scoring problem in the whole business: "who pays" is no longer an open question, the RaaS operator pays for their own tool, same way any business buys its own analytics software.

**What the product actually does now:** takes robot telemetry (task completion, uptime, utilization, fault rates) and turns it into *financial* telemetry, quantifying it into cash flow analysis, cash flow projections, and default/credit risk, specifically for the RaaS operator's own business, plus tracking whether their fleet is hitting the monthly quotas of whatever e-commerce or service contract they've built the RaaS line around. See the new "Financial telemetry" section below for the full reframed product model.

**What stays the same:** the underlying PD/LGD risk-scoring methodology, the technical architecture (connectors → normalization → risk engine → dashboard), and the Bear Robotics Phase 0 bet are all unchanged. What moves is who the dashboard is built for and sold to first.

## Technical architecture

Four layers. Each is intentionally small in scope for a two-person team — the goal is a working, narrow version of each before expanding brand coverage or feature depth.

1. **Robot connectors** — brand-specific integration modules that pull telemetry (uptime, location, battery/utilization, fault codes) from each manufacturer's API or cloud platform. Start with one brand only. **Update 2026-08-04: start with Bear Robotics, not Pudu.** Bear has a fully public gRPC/REST API reference, no partner application needed just to read the schema — `SubscribeRobotStatus` streams `connection`, `battery` (charge_percent + charging state), `emergency_stop`, `mission`, `pose`, `error_codes` (with severity), `navigation_state.stuck_state` (+ reason: path blocked / restricted area / unknown), and `twist` (linear/angular velocity), all in one subscription. Docs: https://cloud.api.bearrobotics.ai/v1.3/resources/RobotStatus/. Pudu's categories are named (Delivery/Return/Cruise/Cleaning/Battery/Abnormal Alert Data) but field-level docs are gated behind becoming a distributor + developer applicant first — treat Pudu as brand #2, not #1, given Bear's docs are readable today with zero gatekeeping. Keenon's API is minimal/unclear from public sources, expanding only in Japan/Korea overseas markets as of last check — lowest priority of the three.
   - **Humanoid robots are a separate, less mature category — relevant because IntBot (see Notes.md) is humanoid.** Unitree has no public cloud API at all, SDK-only over local DDS. Agility Robotics has a cloud fleet platform ("Arc") with no public field-level docs found. Figure/Tesla/UBTECH are earlier still. Don't assume IntBot-style humanoid access will be as easy as Bear's — validate the Phase 0 technical bet against Bear first, pursue an IntBot relationship in parallel on the business side, not as the technical proof point.
   - **Robot-category-aware rules, not one rule set for everything.** Mobility-task robots (cleaning/delivery) being stationary/near-zero-velocity is a fault signal. Interaction/stationary-task robots (a humanoid concierge standing at a desk) being stationary is normal operation. The rules engine needs a robot-category layer from day one or it will misfire constantly on humanoids specifically.
2. **Ingestion + normalization layer** — a common schema mapping every brand's differently-shaped data into one consistent "robot health record," so the dashboard and risk logic don't need to know which brand they're looking at. Note: there's real industry momentum here already — VDA 5050 (German VDA/VDMA-published AMR/AGV fleet interoperability standard, MQTT+JSON, now widely adopted) and MassRobotics AMR Interoperability both standardize position/battery/status across brands already. Normalizing across brands isn't fighting the industry, it's riding an existing trend.
   - **Data-quality / pipe-health layer, separate from robot-health.** Must distinguish "the robot went dark" from "our connection to the manufacturer's cloud went dark." Practical rule: track a connector-level heartbeat (is Botlien's own session/token alive, is the manufacturer's API responding) *separately* from each robot's own last-update timestamp. If one robot goes quiet while its siblings on the same connector keep reporting normally, that's a real robot problem. If every robot on one connector goes quiet at once, that's almost always a pipe/vendor-outage problem, not a fleet-wide coincidence. Cross-check against the manufacturer's own API status page when one exists.
3. **Risk scoring engine** — rules-based at first (not machine learning — ML only makes sense once there's enough historical default/repossession data to train against, which won't exist for a long time). Full methodology, hardened across two adversarial audit passes on 2026-08-04, below.

   **Signal → flag mapping (using Bear's real schema as the concrete example):**

   | Signal | Source field | Flag rule (v1, unvalidated — needs backtesting) |
   |---|---|---|
   | Availability | `connection.state` | Offline > set continuous hours, or offline frequency rising week-over-week |
   | Utilization | `mission` history | Active work time drops > set % vs. trailing 4-week baseline, **per robot type and deployment context**, not one flat number (a hotel robot's normal weekend dip isn't a warehouse robot's normal weekend dip) |
   | Faults | `error_codes` + severity | High-severity code, or same code recurring, or rising error-rate trend |
   | Mobility health | `navigation_state.stuck_state`, `twist` | Repeated stuck events, or near-zero velocity while a mission is supposedly active — **gated by robot category**, see above |
   | Battery health | `battery` over time | Irregular charge cycles, or capacity degrading faster than that robot's own historical baseline |

   **PD vs. LGD — kept as two separate outputs, never blended into one number.**
   - *Probability-of-default-relevant signal:* declining utilization, rising faults, robot going quiet — a proxy for the borrower being unable to afford upkeep or not having enough work to justify the robot, i.e. borrower distress inferred through asset behavior.
   - *Loss-given-default-relevant signal:* current physical condition + depreciated value. **Depreciation, not previously factored in, now is:** collateral value estimate = base depreciated value (age- **and usage-adjusted**, since Botlien has real usage data instead of a blind calendar-only schedule) × a condition multiplier derived from the health/fault score. No "robot Blue Book" resale-comp data exists yet — start conservative (manufacturer-stated useful life, straight-line) until real pilot/resale data accumulates.
   - Why separate: a lender needs both independently — PD answers "should I worry," LGD answers "if I have to repossess this, what do I actually recover."

   **Time horizon — a real gap, not yet resolved.** CECL requires *lifetime* expected credit losses, not a point-in-time snapshot (see Data access model / regulatory section below). A red/yellow/green flag today isn't the same thing as a horizon-calibrated PD. The score eventually needs to project forward over the loan's remaining life, not just report current state — a robot trending down with 6 months left on the loan needs a different lifetime-loss estimate than the same flag with 2 months left. Not solved yet; flagged as a known methodology gap.

   **Portfolio-level view, not built yet.** Everything above is single-robot, single-loan. A lender also needs to see correlated/concentration risk across their whole book — exposure by brand, vertical, geography — so one manufacturer's bad firmware push or one industry's slow quarter doesn't look like 40 independent borrower problems when it's actually one correlated shock.

   **Moral hazard / gaming risk.** Once money is on the line, borrowers have a real incentive to keep a robot moving just enough to avoid tripping flags while other problems go unaddressed. Needs a tamper/integrity check on the signal itself eventually (motion without task completion, activity suspiciously clustered around known reporting windows) — telematics insurance has published real methodology on this exact problem, worth studying before building it.

   **Conflict of interest — needs a stated answer before someone else raises it.** If a RaaS company pays Botlien for internal fleet monitoring *and* a lender relies on Botlien's score to underwrite that same RaaS company, that's structurally close to the issuer-pays rating-agency model criticized after 2008. No answer locked in yet — options are separate commercial relationships with disclosed firewalls, or a lender-pays model specifically for the underwriting-facing product even if the RaaS-facing tool has different economics.

   **Bias/fairness testing — not built, real regulatory precedent that this gets asked about.** Usage-based auto insurance regulators specifically push telematics-based scoring models to be audited for unfair bias (geography, etc.) before full acceptance. Build this in from the start rather than retrofitting after a regulator or lender asks.

   **Model governance — the actual artifact needed before a bank will touch this.** SR 11-7 (Federal Reserve / OCC joint guidance on model risk management) explicitly covers third-party vendor models — a bank using Botlien's score remains on the hook to independently validate it, document it, and monitor performance over time; examiners specifically flag banks that treat a vendor model as a black box. Deliverable needed eventually: a written methodology doc (assumptions, limitations, known unknowns, version history), not just a working dashboard.

   **The APR bridge — Botlien produces the risk input, never the rate itself.** `Expected Loss = PD × LGD × EAD`. That feeds the lender's own pricing formula: `APR = cost of funds + expected loss + capital charge + servicing cost + margin`. Cost of funds, capital charge, and margin are the lender's own proprietary economics — not Botlien's to know or output. Deliverable is a continuously updated, well-documented PD estimate (and separately, an LGD-relevant collateral condition/value estimate) that plugs into a lender's *existing* pricing engine. A startup handing a bank "here's the rate to charge" without a track record reads as overreach, not ambition — this scope boundary is deliberate and should stay firm.

4. **Operator dashboard + alerting** — a simple web view per RaaS operator showing their whole fleet, current status, financial-telemetry KPIs, and a flag list. Email/SMS alerts on flag triggers, nothing more elaborate needed for v1. (Was "lender dashboard" prior to the 2026-08-05 positioning pivot — same underlying build, reframed for the primary customer.)

## Financial telemetry — the product, reframed 2026-08-05

This is the actual pitch now: robot telemetry isn't the end product, it's the raw input. Botlien's job is turning it into something a RaaS operator's own finance function actually uses.

**The pipeline:**
1. **Robot telemetry** (unchanged from the technical architecture above) — uptime, location, battery/utilization, fault codes, mission/task completion events.
2. **Financial telemetry** — the same signals reframed against revenue: task-completion rate against the contract or quota that unit is actually assigned to (a delivery robot's completed-runs count, a warehouse AMR's picks-per-shift, a hospitality robot's service interactions), converted into a realized-revenue-per-robot figure.
3. **Cash flow analysis** — current-period actuals rolled up across the fleet: what the fleet actually generated this month against what it was contracted or projected to generate.
4. **Cash flow projections** — forward-looking, using the same underlying PD-style trend methodology already built for lender-facing risk scoring, just aimed at the operator's own revenue line instead of a bank's default risk.
5. **Default / credit risk** — now framed on the RaaS operator's *own* exposure: if they've financed the fleet themselves (self-leasing to end customers, or carrying their own upstream financing from a bank), the same PD/LGD engine applies, just with the RaaS operator sitting in the position a lender used to sit in for their own book.
6. **Quota / KPI tracking** — are they hitting the monthly targets for whatever e-commerce fulfillment, delivery, or service contract the RaaS line was actually built around, surfaced early enough to act on, not discovered a month later in a bank statement.

**Honest complexity note, not a technicality to skip past:** steps 1-2 are the current MVP scope (Bear Robotics telemetry → normalized health record) and don't change. Steps 2-6 need contract- and billing-specific data that lives in the RaaS operator's own systems, not the robot's API — revenue-per-task, quota targets, contract terms. That's a real integration lift, not a formula layered on top of existing signals. **Recommendation: keep Phase 1 build scoped to telemetry → risk flags as already planned; treat the full financial-telemetry pipeline (steps 3-6) as the roadmap vision that sells the pilot conversation, not the literal v1 build.** Don't let product scope grow as fast as the pitch does.

## Data access model — the actual moat, reframed 2026-08-05

The core defensibility used to rest entirely on data access being a **loan condition** a lender required. With the RaaS operator as the primary, direct customer, that specific legal lock-in isn't the day-one moat anymore — access is now operator-authorized and voluntary, the same as any SaaS tool connecting to a company's own systems. What replaces it, at least until lenders are pulled in downstream: normal SaaS moat mechanics — workflow embedding once a RaaS operator relies on Botlien for monthly quota/cash-flow visibility, and modeling quality that's genuinely hard to replicate without the same accumulated telemetry history. **The loan-condition moat still exists as the expansion layer** — once Botlien has real usage data and a paying RaaS customer base, offering verified fleet data to that operator's own lender becomes a natural upsell, at which point the original contractual lock-in argument re-applies. Flagged honestly: this is a real trade, not a strict improvement, and worth revisiting once there's actual usage data to see how sticky the product proves to be on its own.

- **Consent flow:** the RaaS operator authorizes robot-account API access to Botlien directly, as part of onboarding to the analytics platform — no lender or loan closing required for the primary motion. If a lender is later pulled in as a downstream data recipient, that becomes a separate, additional consent layer (same pattern as connecting a bank account via Plaid, or telematics consent in equipment/auto lending), not the entry point.
- **Data ownership:** the RaaS operator is both the customer and the data source for the primary product. Botlien is the pipe and analytics layer. If/when a lender is added downstream, no party other than the operator's own explicitly-authorized recipients sees that operator's data.
- **Consent chain can still be 3 parties for humanoids — flagged 2026-08-04, still applies.** Manufacturer → RaaS operator → end customer actually operating the robot day to day. A wheeled cleaning robot's uptime data is low-stakes, but a humanoid concierge robot processing voice/video of real people is touching biometric/personal data, a completely different regulatory category. **Hard scope line: Botlien only ever touches non-biometric, non-interaction telemetry — uptime, location, faults, utilization, task-completion events. Never voice, video, or anything involving human interaction data.** State this explicitly in every agreement, don't let it be an assumption.

### Regulatory grounding — why lenders actually need this, not just want it (researched 2026-08-04)

- **CECL (Current Expected Credit Losses, FASB ASC 326):** the real US accounting standard governing how lenders must estimate credit losses. Requires a *forward-looking, lifetime* loss estimate (not "wait until a loss is probable" like the old standard), and explicitly requires considering the nature of collateral and potential future changes in its value. This is the actual regulatory reason a lender needs continuous collateral signal — not optional monitoring, it's already baked into how they're required to estimate losses. Source: https://www.fdic.gov/accounting/current-expected-credit-losses-cecl
- **UCC Article 9:** the law governing security interests in equipment as collateral (literally where "lien" comes from — the root of the company name). Requires lenders to periodically confirm collateral still exists and is in the debtor's possession. Botlien automates an existing legal obligation, doesn't invent a new one. Source: https://uslawexplained.com/uniform_commercial_code_article_9
- **SR 11-7:** Federal Reserve / OCC joint guidance on model risk management, covers third-party vendor models used by banks. A bank remains accountable for independently validating and monitoring any vendor model it uses — can't treat it as a black box. Means the real long-term deliverable isn't just a dashboard, it's a documented, auditable methodology. Source: https://www.modelop.com/ai-governance/ai-regulations-standards/sr-11-7
- **Usage-based insurance telematics is the closest real precedent** for novel IoT/behavioral data getting regulatory acceptance into an actuarial risk model — proof this category of problem (get a regulator comfortable with a new kind of data feeding risk pricing) has been solved once already, in a closely analogous industry. Regulators there have also specifically pushed for bias/fairness audits on telematics scoring models before full acceptance — worth building that in from the start here too. Source: https://actuary.org/article/toward-the-regulatory-adequacy-of-usage-based-insurance/
- **ECOA / Regulation B (fair lending) — audited 2026-08-05, real exposure, not yet fully mitigated.** If Botlien's score influences a credit decision (approval or pricing), it becomes subject to fair lending law. Two concrete exposures: (1) disparate impact — if signals correlate even indirectly with protected characteristics (e.g. deployment geography correlating with race), that's real liability regardless of intent; (2) explainability — adverse credit decisions must be explainable under adverse-action notice requirements. This is the real regulatory reason to stay rules-based instead of moving to ML once more data exists, not just a technical-maturity choice — a documented if-this-then-that rule is far easier to explain in an adverse-action notice than an opaque model.
- **FCRA (Fair Credit Reporting Act) — audited 2026-08-05, likely low risk, conditional on one boundary.** FCRA governs *consumer* credit reporting, not commercial/business credit. Since Botlien's customers are commercial entities (RaaS operators, business lenders), this likely falls outside FCRA's scope entirely. Conditional on staying commercial-only — if this ever extends to an individual/sole-proprietor borrower financing one robot personally, that boundary gets genuinely closer and should be revisited.
- **UCC Article 9 repossession limit, worth restating precisely:** Article 9-609 only permits self-help repossession "without breach of the peace." Botlien can locate collateral; it should never advise on or execute the repossession act itself, that stays a legal/logistics domain outside scope (see hard scope boundary above).
- **Regulatory surface shift, 2026-08-05.** With a RaaS operator as the direct, primary customer instead of a bank, the immediate regulatory exposure is lower: SR 11-7 specifically covers regulated financial institutions using vendor models, and doesn't apply to Botlien's primary sale to a non-bank operator. ECOA/Reg B exposure only resurfaces if the RaaS operator itself uses Botlien's output to make credit or leasing decisions about its own downstream customers, real but now a secondary, later-stage concern rather than a Day 1 constraint. CECL and UCC Article 9 stay relevant as soon as any lender is pulled in downstream, which is still the intended expansion path, just not the entry point.

## Go-to-market sequencing

**Updated 2026-08-05.** RaaS operators are now the primary, standalone customer, not a stepping stone toward lenders. Sequencing: **RaaS operators first and foremost, lenders as a downstream expansion once there's real usage data, robot manufacturers (OEMs) after both.**

- **Why RaaS operators as the direct, primary customer:** a RaaS operator owns its fleet and carries collateral/default risk directly on every unit it leases out — one buyer in the room, no separate lender to convince first, no loan-closing dependency to sell into. It's also selling into the faster-growing market: RaaS is growing at roughly 20% CAGR through 2030 versus the broader equipment finance industry's 10-13% CAGR (sourced 2026-08-05), so the primary customer segment itself is expanding faster than the one originally targeted. It resolves "who pays" outright — the operator pays for their own financial-telemetry tool, no ambiguity about whether the cost lands on the lender or gets pushed to the borrower as a covenant. And it still directly de-risks the "would an OEM steal this" concern — if the RaaS operator is a paying customer instead of just a data source, their incentive flips from competing with Botlien to being aligned with it.
- **Two lending structures still exist as the downstream expansion, now secondary to the direct RaaS-operator sale:**
  - *Asset-backed:* loan secured against one robot's value. Relevant once a RaaS operator's own upstream lender is pulled in as an add-on.
  - *Cash-flow-backed:* a credit facility (warehouse/receivables financing) secured against a RaaS company's *whole book* of lease payments — same structure SaaS companies use for venture debt against MRR. This is the structure Botlien's own financial-telemetry product speaks to most directly even for the RaaS operator itself, since cash flow projection is now core to the product, not just a lender's underwriting input.
- **OEM adverse selection — a real reason to sequence OEMs last.** Participation itself becomes a signal: a manufacturer with reliable robots wants in (better financing terms for their customers = sales advantage), a manufacturer with a rougher reliability record has the opposite incentive. Keep individual OEM performance data private to the lenders financing *that specific OEM's* robots at first — treat cross-brand benchmarking as an explicit opt-in product built later, not baked into the first pilot. Removes the reason a weaker-performing OEM says no.
- **Who to sell to first:** RaaS operators directly, full stop. Not lenders, not large banks (slow, want vendor track record Botlien won't have yet, and no longer the entry point at all).
- **Wedge:** offer the pilot free or near-free to a real RaaS operator in exchange for real usage data and a case study. Year-one goal is proof and a paying, retained operator customer, not lender revenue.
- **Expansion path:** RaaS operators (paying, primary customer) → additional RaaS operators using the case study → that operator's own upstream lender, as a verified-data upsell once real usage history exists → OEMs (as data partners, and where they self-finance, as direct customers) → traditional asset-backed equipment lenders, now the last stop in the sequence rather than an early target.
- **Long-run model — updated 2026-08-05, RaaS operator is now the primary paying tier:**
  - *RaaS operators (primary, immediate customer):* per-robot, $100/month ($1,200/yr) baseline, tiered refinement by robot category still being finalized ($40 delivery / $75 warehouse AMR / $100 hospitality-service / $150 humanoid, pending final lock — see pricing-tier research thread). Anchored against Samsara's fleet telematics pricing ($27–60+/month), priced above it since Botlien carries no hardware/install cost, the underlying assets are higher-value, and the product now includes financial-telemetry/cash-flow analytics on top of raw monitoring, not just uptime alerts. Cheap entry, easy first-pilot yes, revenue scales automatically with fleet growth.
  - *Enterprise RaaS accounts* (large operators, thousands of robots): flat annual contract with a built-in true-up clause at renewal, so growth in monitored fleet size still gets captured instead of given away for free. Standard practice for usage-based SaaS at scale (Twilio, Datadog, Snowflake all do metered pricing for the broad base, negotiated flat contracts for the largest accounts).
  - *Lenders (downstream/secondary tier, not the entry point):* once a RaaS operator is a paying, active customer with real telemetry history, offering verified fleet data and risk scoring to that operator's own upstream lender becomes a natural upsell — sold as a premium add-on or a separate lender-facing product tier, not the first thing Botlien goes to market with.
  - **Rejected after comparison:** a one-time per-loan fee (cost mismatch — Botlien's infrastructure costs are ongoing for the life of the loan/lease, a one-time fee doesn't cover years of hosting/data costs). A pure flat license replacing per-robot entirely (the flat-rate model that underperforms on retention, 95–105% NRR vs. 115–130% for usage-based, per current benchmarks). Annuity/revenue-share tied to performance (no real comparable exists, reads as a services business wearing software's clothes to investors, attribution is hard to isolate).
  - When a lender is involved downstream, Botlien still never outputs the final APR itself — see Risk scoring engine section for the Expected Loss → lender's-own-pricing-formula bridge. That scope boundary doesn't change just because the primary customer did.

- **Why a RaaS operator actually pays — three distinct arguments, not one:**
  1. *Operational visibility:* know instantly if a fleet is falling short of its monthly quota or contract target, before it shows up as a cash-flow surprise at month-end. This is the core "financial telemetry" value prop — see the Financial telemetry section above.
  2. *Planning and reporting:* cleaner cash-flow forecasting for their own internal planning, and sharper, more credible reporting to their own investors, board, or upstream lender if they carry financing themselves.
  3. *Stronger position raising their own capital:* a RaaS operator that can show a lender or investor real-time, verified fleet performance and financial-telemetry history is a more fundable counterparty than one showing spreadsheets, better terms, faster approval, more capital access, the same logic that made telematics valuable to vehicle lenders now applied one layer earlier, to the operator raising the capital rather than the bank extending it.
  - Caveat that doesn't change the priority, it reinforces it: all three arguments depend on the underlying signal actually being predictive of real financial outcomes, still unproven (see Open questions). This is exactly why the pilot and backtest stay the top priority over refining the pitch further.

- **Positioning, sharpened 2026-08-05:** Botlien is not a new financial concept. Fleet financial analytics and asset-backed/performance-based lending are decades old as categories. What's missing is the same real-time, cross-brand visibility layer vehicles already have through telematics (65–85% adoption in financed fleets), never built for robots, and never turned into financial-telemetry analytics for the fleet operator itself. The closer comparable isn't Uber's own driver-financing arm (Uber already has native visibility as a byproduct of being the platform, no third-party data gap to fill), it's third-party fleet lenders and fleet-ops platforms who use vendors like Samsara because they aren't the platform and have no native visibility either, exactly Botlien's position for RaaS operators.

- **Secondary market / re-leasing — new product thread, not yet built, flagged 2026-08-05 so it doesn't get lost:** condition/telemetry history isn't only useful for the *original* loan's risk assessment. Once a robot is repossessed, that same history tells whoever holds it what it's actually worth to re-lease or resell to a *different* operator. No "robot Blue Book" resale-comp dataset exists anywhere yet — this would be built from scratch as real pilot data accumulates. Distinct future product line, not part of the core pre-seed pitch.

- **Hard scope boundary, stated explicitly so it doesn't blur later:** Botlien provides data and visibility only. It never advises on or executes repossession (UCC 9-609 self-help repossession has real "breach of peace" limits — that's a legal/logistics domain outside Botlien's scope), and it never remotely disables or controls a robot. Remote-disable devices are a materially more regulated category (see starter-interrupt device restrictions in some states for auto lending) — a different product than what's being built, and should stay that way even as the product matures.
